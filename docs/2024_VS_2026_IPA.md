# Comparing official ChatGPT iOS 1.2024.200 and 1.2026.272

Source: both user-provided IPAs, inspected as Mach-O frameworks. No proprietary app executable is included in this repository.

## Compatibility boundary

| Detail | 1.2024.200 | 1.2026.272 |
| --- | --- | --- |
| Minimum iOS | 16.1 | **18.0** |
| ChatGPT.framework main binary | 44,607,424 bytes | 178,886,416 bytes |
| Additional OpenAIXPlat.framework | No | Yes (12,978,064 bytes) |
| Main framework encryption cryptid | 0 | 0 |

The 2026 framework is accessible for **static comparison** but it is not an iOS 16 drop-in replacement. It targets newer system APIs and has a substantially different binary/feature layout.

## History: both versions still have independent local sidebar models

The 2024 framework exposes `ChatGPTHistory/HistoryViewModel.swift`, `fetchMoreItems()`, `conversationListRequestTask`, `historyItemsByID`, `_conversationsByID`, `fetchMoreItemsTask`, and `_fetchState`.

The 2026 framework still has `ChatGPTHistory/HistoryViewModel.swift`, `conversationListRequestTask`, `_conversations`, and `fetchMoreItems(reason:)`. It also has named structures `ConversationListFetchDetails` and `ConversationListResponse`, as well as cursor-based conversation fetching methods elsewhere in the framework.

**What this proves:** The old and new UI histories do not have exactly the same internal structure. It does not yet prove whether the actual backend list request changed: that requires comparing authenticated, private-safe server response structures, or tracing the respective Swift call paths. It is unsafe to fabricate hundreds of missing items or assume a successful response layout.

## Existing conversation attachment button

The 2024 message input model includes `_fileUploadBlockedFeature`, `_shouldShowAttachmentsDisabledPopover`, `_productFeatures`, `_isConversationInputDisabled`, and `_uploads`. The 2026 code still has `_fileUploadBlockedFeature` and expanded composer state. Both frameworks have conversation-detail metadata services.

**Observed by the user:** Every existing sidebar conversation lacks the attachment (+) button; chats newly created inside the 2024 app have the button. This is an *existing vs new conversation* distinction, not a PC-only distinction.

**Hypothesis to test:** A value provided by `POST /conversation/init` or a metadata fetch makes the 2024 existing-chat composer treat file uploads as unsupported. Our previous logs only captured `GET /conversation/{id}` (messages); they **did not capture the initialization response**. Therefore those logs cannot establish the cause.

## Why the earlier experiments were inconclusive

The installed ChatGBeFree **2.3.5** contains its own NSURLSession/URLProtocol interception infrastructure. Our v0.1–v0.3 separately registered custom protocol handlers and introduced forwarding, response transformation and, in v0.3, an experimental HTTP 500 retry. The user's log showed first-page GET `offset=0&limit=20` repeatedly when the sidebar was manually refreshed, some HTTP 500 responses, and timeouts. The user reports hundreds of missing conversations; fetching 20 isn't enough unless paging works.

**Important:** Simultaneous interception can distort the result. We must not interpret those errors as proof of an OpenAI server-side issue.

## v0.4.0: passive control test

The 551UK component now does **not** register an NSURLProtocol, alter any NSURLSessionConfiguration, replay requests, alter model names, spoof HTTP responses or modify JSON. It only records sanitized route categories and paging values at `NSURLSessionTask resume`, and optionally inspects **unmodified completion-handler responses** for:
- conversation list: HTTP status and presence/count of an `items` array;
- `POST /conversation/init`: HTTP status, broad presence of model/blocked-feature fields and whether the fields mention an upload restriction;
- conversation detail: basic structural presence, no chat content.

Callbacks using a delegate rather than completion handler may **not** be observed; a lack of `complete route=` entries does not prove a request is stuck. It is a safe first isolation test.

**Test order:** Keep ChatGBeFree 2.3.5, upgrade only the 551UK companion, force-close ChatGPT, open a newly started chat and then a sidebar chat (note the order), refresh sidebar, upload the log from `Library/Caches/ChatGPT551Repair.log` in the ChatGPT app data container. The log must not contain titles, conversation IDs, cookies, tokens, request URLs or message bodies.

The goal is eventually a single editable-source compatibility tweak by 551UK. The 2.3.5 working voice, models and image code is not published as source upstream; it is **not** yet recreated by the 551UK companion and its compiled binary is not redistributed here. Version-specific compatibility and account/server restrictions may limit what can be restored.
